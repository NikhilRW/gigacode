# Download an iOS IPA and build a POCO X4 APK

The app is `apps/expo` (Expo SDK 57 / React Native 0.86). Native projects are generated by Expo
Prebuild; do not commit or hand-edit generated `ios/` and `android/` directories.

## iOS: native-sim

The iOS setup is generated by **native-sim 0.2.2**, using your checkout at `D:\RN_Practice\native-sim`:

```powershell
# Repository-root terminal; scaffolding only, no commit/push/build:
node "D:\RN_Practice\native-sim\bin\native-sim.js" init --framework expo --project-dir apps/expo
```

Generated files are `.github/workflows/native-sim.yml` and the helpers under `.github/native-sim/`.
The earlier custom `expo-ios-build.yml` / `scripts/build-ios.sh` were replaced. GigaCode-specific
adaptations keep the generated streaming/gate/export machinery and adjust:

- **Node 22 / Bun 1.3.13**, with dependencies installed from **`apps/expo/bun.lock`**, not the legacy root lock.
- Expo Prebuild and CocoaPods in `apps/expo`; the Mac runner stays **`macos-26`** (SDK 57 needs Xcode 26.4+).
- IPA export allowed after an **Expo** build, as well as the native Xcode mode supported by the template.
- IPA exports bypass simulator-only native caches so the generated Xcode workspace is present for the device build.
- Complete simulator-build and device-export logs uploaded on failure.

Do not force-refresh the templates without reconciling these adaptations. The upstream CLI's template
version guard retains same-version customizations, but a newer template can require another merge.

### What happened in the failed build?

The supplied `gigacode-ios-build-log-1.zip` ends with **`BUILD SUCCEEDED`**. The full failed-step output
from [run 41442929827](https://github.com/NikhilRW/gigacode/actions/runs/41442929827) reveals that the
old script then called `lipo -verify_arch arm64 <binary>` in the wrong order. Xcode's `lipo` treated
the binary path as an architecture and returned exit code 1. Correct syntax puts the input first:
`lipo <binary> -verify_arch arm64`. The replacement native-sim export helper does not use that check.
The log also confirms `main.jsbundle` was generated inside `GigaCode.app`; this was not a compilation
or missing-JS-bundle failure.

### Build and download the unsigned device IPA

Push the generated workflow and helpers to GitHub first; the workflow must exist on the default
branch for dispatch. The job builds the selected **remote** branch, not uncommitted local changes.

Open PowerShell in **`apps/expo`**:

```powershell
gh auth login  # Once, if GitHub CLI is not already authenticated
bun run ios:ipa
```

This helper dispatches the **generated native-sim workflow** with Expo/build mode, `project_dir=apps/expo`,
Release configuration, no native cache, both exports enabled, and a one-minute stream hold. Session ID
and gate token are generated automatically. It does not commit/push files or start a local Xcode build.
To choose a remote branch or a longer hold:

```powershell
pwsh -NoProfile -File scripts/native-sim-ipa.ps1 -Branch main -Minutes 10
```

Open **GitHub Actions → native-sim** and select the session printed by the helper. The workflow boots
the simulator and builds/launches the app, then compiles a separate **iphoneos / arm64 / Release** device
build and packages `Payload/GigaCode.app`. Download **`native-sim-ipa-<session>`** under Artifacts and
extract GitHub's outer ZIP to obtain **`unsigned.ipa`**. IPA artifacts are retained for **seven days**;
simulator app artifacts (`native-sim-app-<session>`) are retained for **one day**.

```powershell
# From this repository:
gh run list --workflow native-sim.yml --limit 5
gh run download <RUN_ID> -n native-sim-ipa-<SESSION> -D "$HOME\Downloads\GigaCode"
```

If a build/export step fails, download **`native-sim-build-logs-<session>`**. It includes the export
output, not just the compiler log. GitHub-hosted macOS usage/billing depends on your repository/plan.

**CLI compatibility:** the current local native-sim 0.2.2 `up --export-ipa` command rejects Expo projects
before dispatching. Use `bun run ios:ipa` for this repository's Expo IPA export; it targets native-sim's
workflow directly. Do not select `--framework native` for this Expo app merely to bypass that guard.

### Live simulator using the native-sim CLI

Run from the **repository root**:

```powershell
node "D:\RN_Practice\native-sim\bin\native-sim.js" up --framework expo --project-dir apps/expo --no-cache --export --minutes 30 --out "$HOME\Downloads\GigaCode"
```

The CLI prints the authenticated browser preview URL. `--export` downloads the **simulator `.app`
archive**, not an IPA. `native-sim up` automatically commits/pushes changes as part of its normal flow;
review your working tree before invoking it. Its `status` and `down` commands manage CLI-started
sessions. A session dispatched by `ios:ipa` is instead visible/cancellable through GitHub Actions.

For a manual Actions dispatch, use `mode=build`, `framework=expo`, `project_dir=apps/expo`, `dev=false`,
`export_app=true`, `export_ipa=true`, `cache=false`, and supply a unique session/access token.

### API URL and installation

Enter the HTTPS API origin in the installed app's **Connection** screen. A repository Actions variable
named `EXPO_PUBLIC_API_URL` can provide a default; no secrets belong there. The backend remains separate
and must be reachable, as explained in [CODESPACES.md](CODESPACES.md). Release builds embed JS and editor
DOM assets; `--dev` intentionally creates a Metro/development-client build instead.

**`unsigned.ipa` needs Apple signing before normal iPhone installation.** Re-sign the app and embedded
frameworks with an appropriate identity/provisioning profile using your chosen signing/sideload tool,
The iOS client uses basic AsyncStorage and excludes SecureStore from native linking. The native-sim workflow does not
create a signed distribution IPA. The existing EAS preview profile remains available for a signed build:

```sh
# In apps/expo, with your own Expo project and Apple credentials:
bunx eas-cli login
bunx eas-cli init
bunx eas-cli device:create
bunx eas-cli build --platform ios --profile preview
```

On an Apple Silicon Mac, a downloaded simulator archive can be extracted and installed into a booted
simulator with `xcrun simctl install booted GigaCode.app`. It cannot be renamed to an iPhone IPA: the
platform is different even when both binaries are arm64.

## Android: local ARM64 APK for POCO X4

POCO X4 Pro 5G / X4 GT use ARM64-class hardware. Confirm the actual installed OS ABI over USB:

```powershell
adb devices
adb shell getprop ro.product.cpu.abi
adb shell getprop ro.product.cpu.abilist
```

Use **`arm64-v8a`** when it appears in that output. Enable Developer options and USB debugging on the
phone, and accept its USB authorization prompt. If multiple devices/emulators are connected, use
`adb -s <serial>` for device commands.

### Prerequisites

- Windows with **PowerShell 7 (`pwsh`)**, Node **22.13+**, Bun **1.3.13**.
- Android Studio / Android SDK, accepted SDK licenses, platform-tools, and a JDK compatible with the
  generated Gradle project. JDK 21 is available on the current development machine; ensure `JAVA_HOME`
  and PATH refer to your intended JDK.
- Set `ANDROID_HOME` to your SDK directory (commonly `%LOCALAPPDATA%\Android\Sdk`). Install the
  generated project's requested platform/build-tools/NDK/CMake versions through SDK Manager; SDK 57
  targets Android API 36. The first Gradle build downloads substantial dependencies.
- Install **CMake 4.1.2** through Android Studio → SDK Manager → SDK Tools → Show Package Details.
  The app pins it through `expo-build-properties` so the app and native libraries use its **Ninja 1.12.1**.
  Android's older CMake 3.22.1 includes Ninja 1.10.2, which misidentifies long dependency paths as
  missing on this checkout and causes `build.ninja still dirty after 100 tries`. Merely adding a newer
  Ninja to PATH does not fix it: Gradle selects the Ninja bundled with its configured CMake.

### One-command build

Open PowerShell in **`apps/expo`**:

```powershell
bun install --frozen-lockfile

# Optional public API default. Otherwise configure Connection after installing.
$env:EXPO_PUBLIC_API_URL = 'https://your-api.example.com'

bun run apk:arm64
```

`apk:arm64` runs `scripts/build-android.ps1`. It runs Expo Prebuild without clearing an existing native
directory, then executes:

```powershell
.\android\gradlew.bat -p .\android :app:assembleRelease -PreactNativeArchitectures=arm64-v8a --console=plain
```

The architecture flag applies to this build; it does not permanently remove other architectures from
the app's configuration. The output is a **Release APK with embedded JS/assets**, not an AAB and not
a Metro-dependent debug build:

```text
apps/expo/android/app/build/outputs/apk/release/app-release.apk
```

Install it from that same `apps/expo` terminal:

```powershell
adb install -r ".\android\app\build\outputs\apk\release\app-release.apk"
```

Expo's SDK 57 template signs this local Release variant with its generated **debug keystore** by default.
It is suitable for your own sideload/demo, not Play Store distribution. An existing installation signed
with another key cannot be updated with this APK. Uninstalling it removes app data; preserve any drafts
you need first. For publishing, configure a real release key through a config plugin or use the existing
EAS build profiles with managed signing.

### Direct commands without the helper

From `apps/expo`, after installing dependencies:

```powershell
bunx expo prebuild --platform android --no-install --no-clean --skip-dependency-update react,react-native
.\android\gradlew.bat -p .\android :app:assembleRelease -PreactNativeArchitectures=arm64-v8a
```

On Linux/macOS the equivalent Gradle invocation is:

```sh
./android/gradlew -p android :app:assembleRelease -PreactNativeArchitectures=arm64-v8a
```

If Windows CMake/Ninja reports path-length or quoting errors, try a short checkout path such as
`D:\gigacode` before changing native build files. If the SDK location is missing, set `ANDROID_HOME`
in the terminal before the build. No Android emulator is required to produce the APK.

For the Reanimated regeneration loop specifically, install dependencies and rerun `bun run apk:arm64`:
Prebuild now writes `android.cmakeVersion=4.1.2`, and Gradle generates a separate CMake build directory.
The targeted Reanimated/Worklets ARM64 native build has passed with this override in the existing long
checkout path; no manual node_modules edits, dependency downgrades or global Gradle-cache deletion are
needed for that failure.

If the build then says **`No space left on device`** / **`There is not enough space on the disk`**, that
is a separate storage failure, not another Ninja regeneration bug. Native object files, copied libraries
and Gradle/SDK caches can require several GB on both the checkout drive and the system/cache drive.
The Windows helper refuses to start if the checkout drive has less than 1 GiB free; that is an early
failure threshold, not a guarantee that 1 GiB is enough. Prefer at least 5–10 GiB of build headroom.
Free disk space or place a fresh source checkout on a larger drive (for example `D:\gigacode`) and
install dependencies there. Do not copy old `.cxx`/`build` caches to a new path; they embed absolute paths.
Keep your original checkout until all local changes and configuration have been preserved.

After moving/copying the checkout, React Native can reuse
`android/build/generated/autolinking/autolinking.json` with the old absolute directory even when
package files are unchanged. The APK helper now detects that root mismatch and removes only generated
project/module build caches before running Prebuild/Gradle. It preserves native sources, signing keys,
environment files and global caches. Run normally from the new `apps/expo` directory:

```powershell
bun run apk:arm64
```

To explicitly invalidate those caches if the generated metadata is missing or otherwise stale:

```powershell
pwsh -NoProfile -File ./scripts/build-android.ps1 -ResetNativeCache
```

Do not use `gradlew clean` as the first recovery command for an old autolinking path: Gradle can fail
while configuring the nonexistent old module directory, before the clean task can run.

## Verification boundary

Workflow/script syntax, Expo configuration, lint and TypeScript can be checked on this Windows machine.
They do not create an IPA; Xcode runs on the GitHub Mac. Signed builds additionally depend on your Expo
project/token and Apple credentials. The Android command must complete Gradle compilation locally to
produce its APK. No GitHub workflow, signing-account operation or device installation is started just
by adding these files.
